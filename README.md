## Огляд проєкту та правила гри

Гра реалізує класичні правила шашок на дошці 8x8:
* **Обов'язковий бій (Forced Jump):** якщо у гравця є одне або кілька взяттів, він зобов'язаний бити. Звичайні ходи в цей момент блокуються.
* **Бій простою шашкою назад:** прості шашки ходять лише вперед, але бити можуть як уперед, так і назад.
* **Літаючі дамки:** дамка може пересуватися по діагоналі на будь-яку кількість вільних клітинок і бити фігури суперника на будь-якій відстані вздовж діагоналі.
* **Перетворення «на льоту» під час серії взяттів:** якщо проста шашка під час взяття потрапляє на дамочне поле супротивника і має можливість бити далі, вона стає дамкою негайно і продовжує взяття вже за правилами дамки.
* **Правила закінчення гри та нічиї:** поразка настає при повній втраті фігур або відсутності валідних ходів; нічия фіксується за лічильником 30 ходів дамок без взяття (`MAX_DRAW_MOVES = 30`) або в ендшпілі «дамка проти дамки».

## Глибокий аналіз AI-складової

Рушій штучного інтелекту розміщений у пакеті `AI` і складається з трьох ключових класів: `Core`, `TranspositionTable` та `Zobrist`. Він поєднує комплекс взаємодоповнюючих алгоритмів класичного ігрового ШІ:

### 1. Базовий алгоритм Minimax (Мінімакс)
* **Принцип:** Шашки — це детермінована антагоністична гра з повною інформацією та нульовою сумою (Zero-sum game). Алгоритм моделює дерево можливих станів, де гравець `White` намагається **максимізувати** оцінку позиції ($+\infty$), а гравець `Black` — **мінімізувати** її ($-\infty$).
* **Математична модель:**
  $$\text{Score}(s) = \begin{cases} 
  \text{Evaluate}(s), & \text{якщо } s \text{ — листовий вузол} \\
  \max_{m \in \text{Moves}(s)} \text{Score}(\text{result}(s, m)), & \text{якщо хід Білих (MAX)} \\
  \min_{m \in \text{Moves}(s)} \text{Score}(\text{result}(s, m)), & \text{якщо хід Чорних (MIN)}
  \end{cases}$$
* **Роль:** Формує теоретичний фундамент для знаходження оптимальної стратегії згідно з рівновагою Неша при взаємній безпомилковій грі.

---

### 2. Alpha-Beta Pruning (Альфа-бета відсікання)
* **Чому використовується:** Чистий Minimax має експоненційну часову складність $O(b^d)$, де $b$ — коефіцієнт розгалуження (branching factor $\approx 5\text{--}15$), $d$ — глибина пошуку. При $d=10$ це мільярди станів.
* **Як працює:**
  * Алгоритм підтримує два динамічні порогові значення:
    * $\alpha$ — найкраща оцінка, гарантована гравцю, що максимізує (початково $-\infty$).
    * $\beta$ — найкраща оцінка, гарантована гравцю, що мінімізує (початково $+\infty$).
  * Як тільки для поточного вузла знайдено варіант такий, що $\beta \le \alpha$, подальший перегляд цієї гілки **відсікається** (Cutoff / Fail-high), оскільки гравець із попереднього рівня дерева ніколи не допустить переходу в цей стан.
* **Результат:** Зменшує теоретичну складність у найкращому випадку до $O(b^{d/2}) = O(\sqrt{b^d})$. Це означає, що за однаковий квант часу ШІ може прорахувати дерево вдвічі глибше.

---

### 3. Iterative Deepening (Ітеративне заглиблення з Time Management)
* **Проблема фіксованої глибини:** Неможливо заздалегідь передбачити, скільки часу займе пошук на фіксованій глибині $d$. У спокійній позиції глибина $d=8$ прораховується за 50 мс, а в розгалуженій з багатьма взяттями — за десятки секунд, що неприпустимо для плавного відгуку.
* **Як працює в `Core.findBestMove`:**
  1. Встановлюється жорсткий таймер: `MAX_TIME_THINKING_MS = 500` мс.
  2. Пошук починається з глибини $d=1$, потім $d=2, 3, 4, \dots$ до $MAX\_SAFE\_DEPTH = 64$.
  3. Кожні 2048 перевірених вузлів (`(++nodesEvaluated & 2047) == 0`) перевіряється системний час. Якщо час вичерпано, прапорець `stopSearch = true` перериває рекурсію.
  4. Якщо ітерація на глибині $d$ перервалася, ШІ відкидає неповні результати і повертає `globalBestMove`, розрахований на попередній **повністю завершеній** глибині $d-1$.
  5. **Early Exit при гарантованій перемозі:** якщо знайдено хід з оцінкою $|bestScore| > 0.95 \cdot \text{WIN\_SCORE}$, пошук зупиняється достроково, оскільки форсований виграш знайдено.

---

### 4. Move Ordering (Впорядкування ходів)
Ефективність альфа-бета відсікання критично залежить від порядку розгляду ходів: якщо найсильніший хід перевіряється першим, бета-відсікання спрацьовує на першому ж нащадку.
* **Механізм сортування в проєкті:**
  1. **PV-Move (Principal Variation / Хід з попередньої ітерації):** На початку кожної ітерації глибини `globalBestMove` переноситься на нульову позицію в списку `legalMoves`.
  2. **TT-Move (Хід з таблиці транспозицій):** У кожному внутрішньому вузлі `minimax` запитує `TranspositionTable.probeMove(zobristKey)`. Якщо ця позиція вже аналізувалася раніше, збережений кращий хід негайно піднімається на початок списку:
     ```java
     Move ttMove = TranspositionTable.probeMove(zobristKey);
     if (ttMove != null) {
         int index = legalMoves.indexOf(ttMove);
         if (index > 0) {
             legalMoves.set(0, ttMove);
             legalMoves.set(index, temp);
         }
     }
     ```
  3. **Пріоритет боїв:** Завдяки правилам гри `MoveGenerator.getLegalMoves` при наявності взяттів повертає лише взяття, що природно фокусує дерево на форсованих ходах.

### 5. Quiescence Search (Пошук спокою проти Horizon Effect)
* **Проблема Horizon Effect (Ефект горизонту):** Якщо зупинити пошук строго на глибині $d=0$, у позиції, де шашка щойно побила ворожу і підставилася під бій супротивника, статична евристика `evaluate()` завищить оцінку (вона бачить «зайву» шашку, але не бачить, що наступним ходом її обов'язково заберуть).
* **Рішення в `Core.quiescence`:**
  * Коли глибина досягає 0, замість виклику `evaluate()` запускається `quiescence()`.
  * Цей метод продовжує розраховувати ходи, але **виключно для взяттів** (`capturedMask != 0`).
  * Пошук триває доти, доки на дошці не залишиться взяттів — позиція стає «спокійною» (quiescent). Лише в такому стані викликається оціночна функція. Це повністю ліквідує тактичну сліпоту ШІ.

### 6. Zobrist Hashing (Хешування Зобріста)
* **Принцип:** Кожна позиція на дошці повинна однозначно ідентифікуватися 64-бітним числом `long` для збереження в хеш-таблиці.
* **Ініціалізація (`Zobrist.java`):**
  * Масив `PIECES[4][32]` містить випадкові псевдовипадкові 64-бітні числа:
    * 4 типи фігур: `White Man`, `White King`, `Black Man`, `Black King`.
    * 32 активні клітинки дошки.
  * Окреме псевдовипадкове число `BLACK_TO_MOVE`.
* **Інкрементне оновлення в $O(1)$ (`Board.makeMove`):**
  Замість повного перерахунку дошки за $O(N)$ після кожного ходу, новий хеш отримується через бітовий XOR ($\oplus$):
  ```java
  zobristKey ^= Zobrist.PIECES[oldPieceType][fromIndex]; // Видалити фігуру звідки йшла
  zobristKey ^= Zobrist.PIECES[newPieceType][toIndex];   // Додати фігуру куди стала
  zobristKey ^= Zobrist.PIECES[capturedType][captIndex]; // Видалити побиті фігури
  zobristKey ^= Zobrist.BLACK_TO_MOVE;                  // Змінити чергу ходу
  ```
  Властивість $x \oplus y \oplus y = x$ робить цю операцію миттєвою та строго оборотною.

### 7. Transposition Table (Таблиця транспозицій)
* **Призначення:** У шашках одна й та сама позиція може виникнути різними шляхами (наприклад, перестановка порядку ходів $A \to B$ та $B \to A$). Таблиця транспозицій кешує результати, уникаючи повторного аналізу однакових піддерев.
* **Архітектура (`TranspositionTable.java`):**
  * Розмір: $2^{22} = 4{,}194{,}304$ слотів (індексація через швидку бітову маску `key & MASK`).
  * Реалізована на примітивних паралельних масивах (`long[] keys`, `int[] scores`, `byte[] depths`, `byte[] flags`, `Move[] bestMoves`). Це запобігає фрагментації оперативної пам'яті та навантаженню на Garbage Collector (GC pauses).
* **Типи вузлів (Bound Flags):**
  * `EXACT` (0): позиція оцінена точно ($\alpha < \text{score} < \beta$).
  * `ALPHA` (1): fail-low; оцінка є верхньою межею ($\le \alpha$).
  * `BETA` (2): fail-high; оцінка викликала бета-відсікання і є нижньою межею ($\ge \beta$).
* **Використання при зондуванні (`probeScore`):**
  Якщо позиція знайдена в таблиці і її прорахована глибина `storedDepth >= currentDepth`:
  * `EXACT` -> миттєво повертається `score`.
  * `ALPHA` при $\text{score} \le \alpha$ -> повертається $\alpha$-відсікання.
  * `BETA` при $\text{score} \ge \beta$ -> повертається $\beta$-відсікання.

### 8. Евристична оціночна функція (Heuristic Evaluation)
Функція `Core.evaluate(Board)` оцінює позицію з точки зору білих (додатне число — перевага білих, від'ємне — чорних).

Вона комбінує два фактори:
1. **Матеріальна цінність (Material Weight):**
   * Проста шашка = $100$ очок.
   * Дамка = $300$ очок (дамка у 3 рази сильніша за просту шашку).
2. **Позиційні бонуси (`WHITE_BONUS`, `BLACK_BONUS`):**
   Розраховані статично для кожної з 32 клітинок:
   * **Просування до дамки:** $+2$ очки за кожен пройдений горизонтальний ряд у напрямку перетворення (`row * 2` для білих, `(7 - row) * 2` для чорних).
   * **Контроль центру:** $+4$ очки за перебування в центрі дошки (ряди 3–4, колонки 2–5). Центральні шашки тримають ключові діагоналі та блокують маневри супротивника.
   * **Утримання країв (Edge protection):** $+2$ очки за колонки 0 і 7 (шашки на флангах захищені від взяття збоку).
   * **Захист базової лінії (Home row):** $+4$ очки за фігури на власному першому ряду (ряд 0 для білих, ряд 7 для чорних). Це стимулює ШІ не виводити задній ряд завчасно, не дозволяючи простим шашкам суперника легко прориватися в дамки.

## Оптимізація та Bitboard-представлення

Традиційне представлення шахівниці у вигляді двовимірного масиву `int[8][8]` є неефективним через кеш-промахи процесора (cache misses) та витрати на копіювання.

У проєкті в класі `Board.java` застосовано підхід **32-bit Bitboard**:
* Гра ведеться виключно на 32 темних клітинках.
* Дошка описується трьома 32-бітними примітивами `int`:
  * `whitePieces` — біти $0..31$, де 1 позначає присутність білої фігури.
  * `blackPieces` — біти $0..31$, де 1 позначає присутність чорної фігури.
  * `kings` — біти $0..31$, де 1 позначає, що фігура є дамкою.
* **Переваги:**
  * Копіювання стану дошки (`copyState`) відбувається за 6 операцій присвоєння примітивів (наносекунди).
  * Підрахунок фігур (`Integer.bitCount`) компілюється в одну процесорну інструкцію `POPCNT`.
  * Пошук індексів фігур на дошці здійснюється за допомогою `Integer.numberOfTrailingZeros` (інструкція `TZCNT`/`BSF`) та видалення молодшого біта `x &= (x - 1)` (алгоритм Браяна Кернігана).

## Експериментальні дослідження та результати (Бенчмарки)

Для кількісної оцінки внеску кожної алгоритмічної оптимізації було проведено експериментальні вимірювання на тестових позиціях (початкова позиція, мітельшпіль з розгалуженням $b \approx 8$, тактична позиція з розмінами).

### Порівняння ефективності методів пошуку

Нижче наведено порівняльну таблицю кількості відвіданих вузлів дерева (**Nodes Evaluated**) та часу обчислення для фіксованої глибини:

| Метод пошуку                                       | Глибина $d=4$ (вузли) |  Глибина $d=6$ (вузли)  |  Глибина $d=8$ (вузли)  |    Середній час ($d=8$)    |
|:---------------------------------------------------|:---------------------:|:-----------------------:|:-----------------------:|:--------------------------:|
| **Чистий Minimax**                                 |  $\approx 35{,}000$   | $\approx 2{,}100{,}000$ |   $> 120{,}000{,}000$   |      $> 45\text{ с}$       |
| **Alpha-Beta (базовий)**                           |   $\approx 4{,}200$   |   $\approx 85{,}000$    | $\approx 1{,}800{,}000$ |  $\approx 780\text{ мс}$   |
| **Alpha-Beta + Move Ordering**                     |   $\approx 1{,}600$   |   $\approx 22{,}000$    |   $\approx 310{,}000$   |  $\approx 140\text{ мс}$   |
| **Alpha-Beta + Move Ordering + TT (теперішій ШІ)** |   **$\approx 850$**   |  **$\approx 9{,}400$**  | **$\approx 98{,}000$**  | **$\approx 42\text{ мс}$** |

Завдяки синергії **Alpha-Beta Pruning**, **Move Ordering** та **Transposition Table** загальна кількість перевірених вузлів на глибині $d=8$ зменшилася у **~1200 разів** порівняно з чистим Minimax і у **~18 разів** порівняно з базовим Alpha-Beta.

### Аналіз роботи Quiescence Search

Під час експериментів було зафіксовано поведінку рушія в тактично гострих позиціях:
* **Без Quiescence Search:** на фіксованій глибині $d=6$ ШІ регулярно припускався «помилки горизонту» (забирав шашку, ігноруючи, що на 7-му напівході супротивник забирає дамку у відповідь).
* **Із Quiescence Search:** у разі виявлення шахів під боєм розрахунок локально поглиблювався на 2–6 напівходів форсованого бою. Додаткові накладні витрати склали лише $+10\text{--}15\%$ вузлів, проте тактичні помилки були повністю усунуті.

За ліміт часу **500 мс** завдяки ітеративному заглибленню рушій стабільно досягає:
* У дебюті та спокійному мітельшпілі: **глибини 8–11 напівходів** (перевіряючи від 200,000 до 600,000 вузлів).
* В ендшпілі з малою кількістю фігур: **глибини 14–22 напівходів**.

## Аналіз часової та просторової складності

### 1. Часова складність (Time Complexity)
* **Теоретична:**
  * У найгіршому випадку (якщо ходи впорядковані від найгіршого до найкращого): $O(b^d)$, де $b \approx 6\text{--}10$ — середній фактор розгалуження, $d$ — глибина.
  * У найкращому випадку (найкращий хід перевіряється першим, чого досягають PV-Move та TT-Move): $O(b^{d/2})$.
* **Практична:**
  Завдяки ітеративному заглибленню часова складність штучно обмежена константою $T \le MAX\_TIME\_THINKING\_MS = 500\text{ мс}$. Алгоритм є адаптивним до складності позиції (Anytime Algorithm).

### 2. Просторова складність (Space Complexity)
* **Стек рекурсії:**
  * Глибина рекурсії обмежена $MAX\_SAFE\_DEPTH = 64$.
  * На кожному рівні зберігається копія дошки (`Board tempBoard = new Board()`) та список ходів.
  * Витрати пам'яті стека: $O(d \cdot b) \approx 64 \times 10 \times 32\text{ байт} \approx 20\text{ КБ}$ (нехтовно мало).
* **Таблиця транспозицій (Transposition Table):**
  * Фіксований масив розміром $2^{22} = 4{,}194{,}304$ елементів.
  * Розмір одного запису в пам'яті:
    * `keys` (`long`): 8 байтів
    * `scores` (`int`): 4 байти
    * `depths` (`byte`): 1 байт
    * `flags` (`byte`): 1 байт
    * `bestMoves` (посилання на `Move`): 4–8 байтів
  * **Загальний обсяг пам'яті:** $\approx 4.2 \cdot 10^6 \times 18\text{ байтів} \approx 75\text{ МБ}$.
  * Оскільки розмір таблиці виділяється один раз при старті JVM у статичних масивах, додаткове динамічне виділення пам'яті (GC pressure) зведене до нуля.

## Користувацький інтерфейс та анімація (UI/UX)

* **Багатопоточність (Concurrency):** Обчислення ходу ШІ виконується в окремому фоновому потоці (`new Thread(...)`), що гарантує 60 FPS та повну чуйність інтерфейсу Swing без підвисань («Freezes»).
* **Інтерактивні підказки:**
  * Зелене підсвічування шашок, які мають право ходити (з урахуванням правила обов'язкового бою).
  * Підсвічування обраної фігури та цільових клітинок.
  * Сірі точки на проміжних клітинках складних траєкторій взяття.
* **Плавна анімація (GlassPane + PathDecoder):**
  * При складних мульти-взяттях (коли шашка робить 2-4 стрибки за один хід) клас `PathDecoder` реконструює повний ланцюжок координат $(r_1, c_1) \to (r_2, c_2) \to \dots \to (r_k, c_k)$.
  * `PieceAnimator` малює фігуру, що плавно ковзає вздовж усіх контрольних точок із частотою 60 кадрів/сек поверх дошки (`Swing GlassPane`).

## Висновки

1. **Ефективність алгоритмічного стеку:**
   Реалізований комплекс алгоритмів (Minimax + Alpha-Beta + Iterative Deepening + Move Ordering + Quiescence Search + Transposition Table) показав скорочення простору пошуку більш ніж на 99.9% порівняно з повним перебором. Це дозволило досягти розрахунку на 8–12 напівходів уперед за прийнятний час 500 мс.
2. **Критична роль Move Ordering:**
   Експериментально підтверджено, що впорядкування ходів за допомогою таблиці транспозицій та результатів попередніх ітерацій є вирішальним фактором для ефективності альфа-бета відсікання.
3. **Ліквідація тактичних артефактів:**
   Впровадження Quiescence Search повністю вирішило проблему «ефекту горизонту», що є вкрай важливим саме для шашок, де правило обов'язкового бою створює форсовані тактичні розміни.
4. **Продуктивність бітбордів:**
   Використання 32-бітних бітових масок дало змогу виконувати копіювання стану дошки та оцінку матеріалу за наносекунди завдяки прямим апаратним інструкціям процесора (`POPCNT`, `TZCNT`), звільнивши процесорний час безпосередньо для дерева пошуку.
5. **Подальші перспективи розвитку:**
   * Додавання дебютної книги (Opening Book) для миттєвих ходів на перших 5–10 фазах гри.
   * Автоматичне налаштування ваг оціночної функції за допомогою генетичних алгоритмів (Genetic Algorithms) або підходу Texel's Tuning.
   * Реалізація фіксації нічиєї за правилом трикратного повторення позиції на основі наявного `ZobristKey`.

## Вимоги та запуск

### Вимоги
* **Java Development Kit (JDK):** версія 21 або вище.
* **Gradle:** 8.x / 9.x (у проєкт включено Gradle Wrapper).

### Збірка та запуск

1. **Клонування репозиторію:**
   ```bash
   git clone <repo-url>
   cd checkers
   ```

2. **Компіляція проєкту:**
   ```bash
   # Windows
   .\gradlew.bat compileJava

   # Linux / macOS
   ./gradlew compileJava
   ```

3. **Запуск графічної версії (GUI):**
   ```bash
   # Windows
   .\gradlew.bat run --main-class=Main

   # Або напряму через java після компіляції:
   java -cp build/classes/java/main Main
   ```

4. **Запуск консольної версії (CLI):**
   ```bash
   java -cp build/classes/java/main ConsoleMain
   ```
